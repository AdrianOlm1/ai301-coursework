# Rubric: is this pull request ready to submit?

A PR package is the plan the PR claims to implement, the candidate PR (title, description, commits, diff, test evidence), and the repo's stated asks. Every package is treated as AI-assisted work, whoever wrote it. Grade what the artifacts contain, never how long or polished they are. A short, complete PR is ready. A PR that honestly discloses a shortfall can be ready.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | Every changed file and every hunk in the diff, read against the plan's "Scope", "Files" and "Not in scope" statements and any deviation note in the plan or restated in the description | Every changed file and hunk falls inside the plan's stated scope or is covered by a deviation note, AND everything the plan promised (a code change, a test, a docs or changelog update) appears in the diff or is explicitly disclosed as deferred. Fail if the diff contains a file, hunk, option, flag, rename, or rewrite the plan did not name and no note covers (more than the plan), or if a promised piece is absent and nothing says so (less than the plan). A disclosed deferral or deviation passes. | required |
| description-matches-diff | Each factual claim in the description ("implements the plan exactly", "no options added", "docs now document", "tests added", checklist items) read against the diff and the commits | Every claim about what the PR changes, adds, or leaves out is true of the diff. Fail if the description claims fidelity or completeness that the diff contradicts (claims no changes beyond the plan over a diff with an unplanned file, or claims a docs update the diff does not contain). | required |
| test-evidence-decisive | The test-evidence section read against the plan's test plan and the repro evidence's steps | The evidence re-runs the plan's repro, or the failing path the repro names, on the changed code, and shows an observable before and after (a command with its printed output, or a stated before and after outcome). When the plan's test plan names more than one failure mode, each is shown, or the omission is stated. Fail if the evidence is "tested locally", "tests pass", or "works on my machine" with no repro re-run; if it exercises a control or the unchanged path instead of the changed one; or if the added test does not cover the fix. | required |
| diff-reviewable | The added lines of the unified diff and the commit list | The change is the fix and its test, with no debris in the added lines: no debug prints or logging left behind, no commented-out code, no dead or unused function or import added, no formatting or re-indent churn hunks, no unrelated edits, no TODOs unrelated to the change. An explanatory comment about why the code does something is not debris. Fail if any such debris appears. | required |
| template-asks-met | The repo-facts block's PR-template asks (or the repo's PR template in live mode), read against the description and the diff | Every ask the repo states for a PR is met: each required section has real content, an issue is linked as the template asks, each checklist item that is ticked or claimed is true of the diff, and a required artifact (changelog or whatsnew entry, tests, docs) is present in the diff. Fail if a stated ask is visibly ignored. Pass if the repo states no ask. | required |
| ai-disclosure | The repo-facts block's contribution policy line, read against the description (live mode: the course's own ask, in the template's Notes for Reviewers) | If the policy requires AI-use disclosure, or this is live mode where the course asks for it, the description states in plain words that AI was used and how. Fail if a required disclosure is absent. Pass if the policy states no disclosure requirement and the package is an eval bundle. | required |
| repo-checks-named | The test evidence, read against the commands the PR template or contributing guide lists | The evidence names each of the repo's own check commands the template lists and shows its result. | preferred |

## Verdict rule

Accept (ready to submit) if every `required` check is `pass`. Reject (hold) if any `required` check is `fail`. An `unclear` on a required check counts as `fail`, except that `template-asks-met` and `ai-disclosure` are `pass` when the package states no ask or no disclosure requirement to meet. `preferred` checks never change the verdict.
