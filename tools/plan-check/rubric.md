# Rubric: is this plan ready to post and build from?

A "package" is the issue context, the repro-evidence block, the candidate plan, and the candidate plan comment. Every package is treated as AI-assisted work, whoever wrote it. Grade the thing itself, never the write-up's length, headings, or polish.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-matches-repro | The plan's stated cause (its "Diagnosis" or "Cause" statement) read against the repro-evidence block: every numbered step, the artifact or output, and every control run | The stated cause explains EVERY step and EVERY control run in the repro evidence. Fail if any control run or step contradicts it (for example, a control run that behaves correctly with the blamed component still in the loop), or if the plan never mentions the controls and blames a different component than the one the evidence isolates. A cause taken from a maintainer's or reporter's guess in the thread is only as good as the repro evidence that supports it; the thread is not evidence of the cause. | required |
| scope-bounded | The plan's in-scope statement, its not-in-scope line, and the list of files or areas it names, read against the issue title and body | The plan changes ONE thing the issue asks for, names the files or areas it will touch, AND says what it will not touch. Fail if the plan adds work the issue never asked for (a refactor, a migration, a new option or setting, a redesign, a dependency or runtime upgrade, "while I'm in the area" cleanups), or if the one bounded fix is bundled with such work. Deferring a related symptom explicitly, with a reason, is bounded and passes. | required |
| executable | The plan's approach: the files or areas, the chosen approach, the order of work | A stranger could start work without asking the author anything: the plan names where the change goes (a file, module, or component) and commits to one approach, meaning it says what the change does. Fail if the approach is "investigate", "profile", or "poke around", if a real DECISION about where or how is deferred to build time (a choice between layers, approaches, or locations: "whichever is easier", "somewhere", "gocui? tcell? not sure", "maybe also check"), or if no file, module, or area is named. Naming the module and the change but leaving the exact function or line to be found by tracing is NOT a deferred decision and passes. A short plan that names the file and the change passes. | required |
| test-observable | The plan's test plan, read against the repro-evidence steps | The test plan names a specific observable result that distinguishes fixed from broken, such as the repro steps re-run with the expected output, or a named test that fails before the change and passes after. Fail if the test plan is "run the full test suite", "should feel fast", "nothing else should break", or otherwise names no outcome the fix itself must produce. | required |
| thread-aware | The plan comment read against the "Thread highlights" section of the issue context | If a maintainer or owner gave explicit direction in the thread (a settled approach, a located culprit, a rejected approach, an open PR or prior art to engage, a request to test something), the plan comment follows that direction or says why it departs from it, and the plan does not contradict it. Fail if the comment ignores explicit maintainer direction, or proposes a different kind of change (for example documentation only) than the direction asks for, without engaging it. Pass if the thread has no comments or no explicit direction. | required |
| policy-compliance | The plan comment read against the repo-facts block's "contribution policy" and "bug reports" lines | If the contribution policy states that AI use must be disclosed, the plan comment itself contains a disclosure naming the tool and the extent of AI assistance. If the policy states other requirements the comment can meet (a human-voiced comment, a template ask), the comment meets them. Fail if a stated requirement is absent from the comment. Pass if the policy is silent, or states no disclosure or comment requirement. | required |
| honest-unknowns | The plan's risks and unknowns, and any hedges in the plan comment | The plan separates what the repro evidence confirms from what is still unknown, and states real unknowns as unknowns instead of certainty. | preferred |

## Verdict rule

Accept (ready to post and build from) if every `required` check is `pass`. Reject (hold) if any `required` check is `fail`. An `unclear` on a required check counts as `fail`, EXCEPT that thread-aware and policy-compliance are `pass` when the package's thread highlights or policy line state nothing to comply with. `preferred` checks never change the verdict.
